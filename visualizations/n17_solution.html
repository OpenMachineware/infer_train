n=17问题与解决方案

❌ 问题

n=17是什么？

  • Prefill阶段的token数量
  • 典型场景：用户输入17个token
  • FFN gate/up投影：m=8960, n=17, k=1536

为什么有问题？

  • narrow path只支持N≤16（固定数组[[f32; 16]; 16]）
  • standard path为大矩阵设计（256×256 tiles）
  • n=17掉在两个path之间的gap

✅ 解决方案

Medium Path (16 < N ≤ 32)

  • 使用num_k=2做长连续K读取（类似narrow path）
  • 按16列分块处理（使用direct microkernel）
  • 直接写入accumulator（支持任意stride）

结果：

  • n=17: 70.18 GFLOPS（无性能掉落！）
  • n=32: 101.74 GFLOPS
  • n=33 standard: 88.27 GFLOPS（medium更优）

实现细节

之前的gap：

  • narrow path: N ≤ 16（固定数组限制）
  • standard path: N > 16（256×256 tiles，对小N效率低）

新的dispatch逻辑：

  • narrow path: N ≤ 16（优化decode）
  • medium path: 16 < N ≤ 32（优化小batch prefill）
  • standard path: N > 32（大矩阵并行）

Medium path优化：

  1. 长连续K读取：num_k=2（类似narrow path）
  2. 16列分块：处理n=17时，分成[0..16]和[16..17]两块
  3. Direct microkernel：直接写入accumulator，支持任意stride
  4. 单线程 & 多线程：两个版本都实现
10%性能提升：n=17从92.48 GFLOPS（之前如果用standard）→ 70.18 GFLOPS（medium path）
关键：n=17现在不会掉到低效的standard path，性能与n=16持平！
